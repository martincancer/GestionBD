Auditoría de tablas
en SQL Server

Cómo registrar automáticamente quién cambió un dato, cuándo lo hizo y cuál era el valor anterior y el nuevo, usando una tabla de auditoría y triggers DML.

¿Qué es la auditoría de tablas?

Auditar una tabla significa dejar rastro de cada modificación importante sobre los datos: qué registro cambió, qué operación ocurrió, quién la ejecutó, cuándo sucedió y qué valores había antes y después.

En producción, la auditoría ayuda a responder preguntas concretas: quién eliminó un registro, cuándo cambió un precio o qué valores tenía una fila antes de una actualización.
LOG

Tabla separada

La auditoría normalmente se guarda en una tabla propia para no mezclar historial con datos operativos.

TRG

Trigger automático

Un trigger AFTER INSERT, UPDATE, DELETE inserta el evento de auditoría sin depender de la aplicación.

CTX

Más contexto

Además del cambio, conviene guardar usuario, host, aplicación y datos clave del registro afectado.

SQL

Historial consultable

Después podés consultar el historial completo ordenado por fecha y reconstruir la secuencia de cambios.

Flujo general de auditoría

Se agrega, modifica o borra un registro
→
Se activa el trigger
→
Lee inserted/deleted
→
Guarda una fila en Auditoría
i
Este enfoque funciona muy bien en sistemas medianos porque es compatible con cualquier edición de SQL Server, incluso Express.

Diseño de la tabla de auditoría

La tabla de auditoría debe capturar el contexto mínimo del cambio para que el historial sea realmente útil cuando haya que investigar qué pasó.

Qué conviene guardar
  • Tabla afectada
  • Tipo de operación
  • Fecha y hora
  • Usuario SQL, host y aplicación
  • Clave del registro
  • Valor anterior y valor nuevo
Por qué importa

Si solo guardás “hubo un cambio”, la auditoría queda incompleta. El valor real aparece cuando podés reconstruir qué registro cambió y comparar antes vs. después.

tabla_auditoria.sql 
CREATE TABLE dbo.Auditoria (
    AuditoriaID   INT            IDENTITY(1,1) PRIMARY KEY,
    Tabla         VARCHAR(100)   NOT NULL,
    Operacion     CHAR(1)        NOT NULL,   -- I / U / D
    FechaHora     DATETIME2(3)   NOT NULL DEFAULT SYSDATETIME(),
    UsuarioSQL    SYSNAME        NOT NULL,
    Aplicacion    NVARCHAR(128)  NULL,
    Equipo        NVARCHAR(128)  NULL,
    ClaveRegistro NVARCHAR(100)  NOT NULL,
    ValorAnterior NVARCHAR(MAX)  NULL,
    ValorNuevo    NVARCHAR(MAX)  NULL
);
Dato clave

Operacion suele guardarse como I, U y D para distinguir inserción, actualización y eliminación.

Diseño práctico

Guardar ValorAnterior y ValorNuevo permite reconstruir el historial completo del registro afectado.

Auditoría con trigger DML

El enfoque clásico es disparar un trigger sobre la tabla que querés auditar y escribir una fila en dbo.Auditoria cada vez que ocurra un INSERT, UPDATE o DELETE.

!
El trigger debe pensar en múltiples filas, no en un solo registro. inserted y deleted pueden traer varias filas afectadas por una sola sentencia.
trigger_auditoria_productos.sql 
CREATE OR ALTER TRIGGER tr_Auditoria_Productos
ON dbo.Productos
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- Inserciones
    INSERT INTO dbo.Auditoria (
        Tabla, Operacion, UsuarioSQL, Aplicacion, Equipo,
        ClaveRegistro, ValorAnterior, ValorNuevo
    )
    SELECT
        'Productos',
        'I',
        SYSTEM_USER,
        APP_NAME(),
        HOST_NAME(),
        CAST(i.ProductoID AS NVARCHAR(100)),
        NULL,
        CONCAT('Nombre=', i.Nombre, '; Precio=', i.Precio)
    FROM inserted i
    LEFT JOIN deleted d ON d.ProductoID = i.ProductoID
    WHERE d.ProductoID IS NULL;

    -- Actualizaciones
    INSERT INTO dbo.Auditoria (
        Tabla, Operacion, UsuarioSQL, Aplicacion, Equipo,
        ClaveRegistro, ValorAnterior, ValorNuevo
    )
    SELECT
        'Productos',
        'U',
        SYSTEM_USER,
        APP_NAME(),
        HOST_NAME(),
        CAST(i.ProductoID AS NVARCHAR(100)),
        CONCAT('Nombre=', d.Nombre, '; Precio=', d.Precio),
        CONCAT('Nombre=', i.Nombre, '; Precio=', i.Precio)
    FROM inserted i
    INNER JOIN deleted d ON d.ProductoID = i.ProductoID;

    -- Eliminaciones
    INSERT INTO dbo.Auditoria (
        Tabla, Operacion, UsuarioSQL, Aplicacion, Equipo,
        ClaveRegistro, ValorAnterior, ValorNuevo
    )
    SELECT
        'Productos',
        'D',
        SYSTEM_USER,
        APP_NAME(),
        HOST_NAME(),
        CAST(d.ProductoID AS NVARCHAR(100)),
        CONCAT('Nombre=', d.Nombre, '; Precio=', d.Precio),
        NULL
    FROM deleted d
    LEFT JOIN inserted i ON i.ProductoID = d.ProductoID
    WHERE i.ProductoID IS NULL;
END;

Contexto del cambio y pseudotablas

El trigger no solo puede guardar datos del registro. También puede guardar metadatos sobre la sesión y apoyarse en inserted y deleted para entender qué pasó en cada operación.

Operación inserted deleted
INSERT Valores nuevos Vacía
UPDATE Valores nuevos Valores anteriores
DELETE Vacía Valores eliminados
SYSTEM_USER

Devuelve el usuario SQL que ejecutó la operación.

HOST_NAME()

Permite registrar desde qué equipo o cliente llegó la modificación.

APP_NAME()

Muestra la aplicación desde donde se ejecutó el cambio, útil para auditoría por sistema.

✓
Si querés saber desde qué aplicación se hizo el cambio, la función correcta es APP_NAME().

Ejemplo práctico de uso

Después de crear la tabla de auditoría y el trigger, podés probarlo con operaciones reales sobre dbo.Productos y luego consultar el historial generado.

pruebas_auditoria.sql 
-- Inserción
INSERT INTO dbo.Productos (ProductoID, Nombre, Precio)
VALUES (999, 'Teclado mecánico', 95.00);

-- Actualización
UPDATE dbo.Productos
SET Precio = 120.00
WHERE ProductoID = 999;

-- Eliminación
DELETE FROM dbo.Productos
WHERE ProductoID = 999;

-- Consultar la auditoría
SELECT *
FROM dbo.Auditoria
ORDER BY FechaHora DESC;
  • 1
    Insert: genera una fila de auditoría con valor nuevo y sin valor anterior.
  • 2
    Update: guarda el estado anterior desde deleted y el nuevo desde inserted.
  • 3
    Delete: conserva el valor eliminado en deleted para no perder rastreabilidad.
  • 4
    Consulta final: permite revisar el historial ordenado por fecha.
Ventaja

La auditoría queda desacoplada de la aplicación: si cambia el front-end, el historial sigue registrándose igual.

Cuidado

Si el trigger se vuelve muy pesado o audita demasiadas columnas, puede impactar el rendimiento de escrituras frecuentes.
